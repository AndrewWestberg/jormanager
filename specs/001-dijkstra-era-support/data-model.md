# Dijkstra data model

**Status:** proposed logical model for implementation, not an applied schema. Storage remains PostgreSQL with Liquibase; Kotlin persistence follows existing Exposed ledger tables and JPA configuration entities. Exact wire rules and source authority remain in [research.md](research.md). External verification blockers are in [plan.md](plan.md).

## Identity and representation invariants

- A network key includes magic, system start and authoritative genesis identity for that network; for Musashi this identifies the selected reset. Magic 164 can be reused after a reset; do not merge its old/new state. Configuration bundle identity is separate: a topology-only update need not create a new chain identity.
- A chain point is `(slot, headerHash)` or origin; block height alone cannot identify a branch.
- `TxId` is the member body hash. `FullTransactionHash` is a distinct EB commitment. Parent linkage never replaces child identity. Preserve original hash-bearing byte slices and their provenance; do not hash a generic re-encoding.
- On-chain facts are occurrence-scoped. The same transaction may occur on a discarded and a later adopted branch. Current effective outputs have unique `(network, TxId, localOutputIndex)` references; occurrence history is not constrained to a single global inclusion.
- Kotlin `BigInteger`, PostgreSQL exact `numeric` with scale zero and field-specific bounds, and decimal-string JSON carry quantities. No `Long` narrowing for unsigned 64-bit values; no JavaScript `Number` for coin/token arithmetic. Use bounded primitive integers only for proven-safe enum/index fields. Preserve rational numerator/denominator exactly, with positive denominator; display decimals are derived.
- Hashes, addresses, asset names, CBOR, datums and scripts are byte-preserving values (`bytea` in PostgreSQL). Asset identity is `(policyBytes, assetNameBytes)`, including zero-length/non-text names. Text labels/images are presentation metadata, never identity.
- Raw presence (`absent`, `null`, `present`) is retained where required. Nonempty ledger collections cannot be normalized to an omitted value; sequence order is persisted. A raw structured payload complements typed fields but does not replace required interpretation.

## Validation and processing order

Read the full batch before committing anything. Dijkstra top-level body keys require inputs/outputs/fee; child keys require inputs/outputs and forbid fee, collateral, further children and starting-balance intervals. Child collections are ordered and nonempty; duplicate body identities fail even when witness sets differ. Keep per-era duplicate and nonempty rules in the decoder, before a general map can erase the evidence.

Dispatch each block by its own authoritative envelope era for ingestion and historical replay, including previously supported eras; write selection instead uses the target network's node-derived current-era cache. On startup and re-established target context query the verified node; a block whose era differs from the cached value triggers `refresh_required` and a fresh node query, while a matching block reuses the cache. A historical or mismatching block never updates the cached current era. Only a successful matching-network node response does so. Pending, failed, unknown or wrong-network evidence blocks dependent writes without disabling other networks or read-only history. There is no era TTL, periodic polling or unconditional query per write; source/point/time are provenance. Confirmed changed era invalidates dependent capability/parameter assumptions and previews, requiring applicable qualification and renewed review; a same-era refresh of provenance alone does not invalidate an otherwise unchanged review. Revalidate cache state at the write boundary along with independently required state, capability and credential checks. Keep earlier-era decoders and workflows as intentional supported paths, not duplicate writers.

For successful batches: snapshot original UTxO/accounts; process children in order, then parent. Account interval checks occur at each member entry, starting intervals use the original pre-batch state, then withdrawals/certificates/direct deposits follow the baseline. Aggregate withdrawals cannot create spendable funds from same-batch deposits. Aggregate value, fees and execution limits apply at batch level. Shared scripts do not merge member-owned datums/redeemers. Interpret older-script mode using the pinned rules, not a blanket ban.

For phase-2-invalid adopted batches: retain member records and unsuccessful inclusion, but mark ordinary UTxO/mint/account/certificate/governance effects ineffective. Apply only reference-prescribed collateral effects at the top level. Structural failure, duplicate children or incomplete closure commits no member effects at all. Independent reference acceptance is required for nuanced restrictions; JorManager does not implement a new full validator.

### Explicit directDeposits mapping

`directDeposits` is the nonempty reward/account-address-to-coin map at Dijkstra body key **25**, allowed on both the top-level member and a child. It is not CIP-159's proposed multiasset account map or key 23. Decode its addresses as bytes and its amounts exactly, preserving the raw map for hash fidelity and duplicate validation. An absent field differs from an explicitly supplied empty/null field; acceptance and amount boundaries follow the pinned decoder/ledger, not a guessed positive-only restriction.

For each entry persist `AccountEffect(kind=DIRECT_DEPOSIT, memberId, accountAddressBytes, amount, operationOrder, inclusionId, effective)`. Account identity includes the network. The semantic destination is the account/reward balance, not a new payment UTxO; the deposit is not a pool/stake registration deposit or fee. Include it once in the batch's accounting and account projection, retaining its owning parent/child even when that member creates no payment outputs.

Apply direct deposits after that member's withdrawals and certificates, subject to account-existence/network rules; same-member registration-before-deposit and child-to-parent account checkpoints require independent reference fixtures. A credit earlier in the batch does not increase the original-balance withdrawal allowance. Script-failed batches retain inspectable deposit intent with `effective=false` and apply no direct-deposit credit. Rollback reverses the account credit and all related state atomically; duplicate direct or certified delivery cannot credit it twice.

Transaction queries expose `directDeposits` and account balance views distinguish these credits from rewards, withdrawals, registration deposits and UTxO funds. Pending deposit intent remains separate from confirmed account funds. Exact client representation is defined in the operator contract; [quickstart.md](quickstart.md) Q2a is the dedicated acceptance scenario.

## State transitions

- Inclusion content: `observed → acquiring → complete` or `incomplete/unsupported/failed`; only complete adopted content advances SyncState. A restored missing closure can resume at the gap. A rolled-back occurrence remains historical, never current.
- Submission: `previewed → authorized → submitted|uncertain|rejected → confirmed`; rollback changes confirmation to `rolled_back` and requires reconciliation. A child cannot enter this machine independently. Local pending UTxOs never enter CurrentUtxo as confirmed funds.
- Key material: `prepared/imported → validated → retained`; registration, eligibility, selection and installation evolve independently. Public registration can exist without local material. Expiration or rollback does not imply secret deletion; the inspected Musashi pool rule does not establish a BLS reservation machine.
- Installation: `not_installed → installing → installed → loaded`, with failure/unknown/stale states. An authorized restart/reload is an external effect, never part of a database rollback.
- Configuration: `discovered → downloading → validated/selectable → explicitly selected → installed → running/synchronized`, with failed/incomplete states at boundaries. A later bundle/reset is a new selection, not an automatic transition of existing nodes. New-pool registration adds its separate authorized/confirmed/key-loaded observations.

## Atomicity, concurrency and recovery

Serialize ingestion and explicit rollback per network. Acquisition/decoding happens outside the database transaction with a bounded in-flight set and captured generation. Recheck generation and predecessor under the commit lock; reject stale branch work. Within one Exposed transaction persist all raw inclusion/member records, projections, reversible changes and complete point. Keep JPA configuration mutations out of this chain commit path unless they participate in the same actual database transaction; do not assume annotations make two transaction managers atomic.

Common batch/member and ordinary MemberData mappings are shared by supported eras; Dijkstra nested semantics use those same mappings. Pool certificate/deposit/refund decoding, reversible projection and operation confirmation effects commit through this same ingestion authority; node queries may supplement observations but never substitute for chain adoption.

Only after successful commit invalidate/rebuild dependent in-memory caches and emit topic updates. On reconnect/restart derive state from the database. Current cache expiry and first-replacement-block rollback are not correctness mechanisms. No CLI submission or SSH side effect runs inside the ingestion transaction.

An explicit rollback reverses all adopted inclusions after the exact intersection, restores spent outputs and account/governance/key observations, changes authorized-operation confirmations, and moves completeness to the greatest complete retained ancestor. If the intersection predates retained history, expose unavailable/replay-required state and rebuild from a verified anchor; never claim rollback success from an incomplete undo set. Retain reversible data through the supported node security/rollback horizon; until that horizon is verified, do not prune Dijkstra reversible history. Deeper rollback uses documented backup/replay rather than guessed state.

## Liquibase upgrade and cutover

1. Back up database plus encrypted credential files and protected configuration; rehearse restore on an isolated instance. Stop ingestion while changing persistence ownership. Existing installation may have multiple configured networks; derive assignments from verified chain/genesis evidence, and block ambiguous data rather than guessing.
2. Add tables/columns, exact-value types and named FK/unique/check constraints using the next available Liquibase changesets, backward-compatible with existing Conway installations. Do not manufacture Dijkstra keys, state, bundle assignments or provenance. Preflight existing duplicate output/asset references and invalid numeric representations. Repair through proven replay, not arbitrary row deletion. Validate existing historical identifiers without rewriting them from re-encoded CBOR.
3. Legacy rows lack original bytes, transaction order/validity and complete membership. Retain known historical IDs/configuration and mark their coverage explicitly. Obtain a replay source back to the required historical anchor; a synthetic metadata backfill cannot manufacture completeness.
4. Replay all required content and projections through the new ingestion path; compare with a fresh database at the same point. Replay failure leaves dependent data stale/unavailable and spending disabled where necessary. Local migration never upgrades remote binaries/genesis/services.
5. Switch all ledger queries, monitors, pending reconciliation and Vue consumers to the new authoritative state. Keep the useful existing UTxO tables as the new maintained projection; remove obsolete duplicate parser/commit/resubmission behavior in the same cutover, while retaining supported earlier-era dispatch and workflows. Do not maintain two independent writers or add a compatibility alias path.
6. Release only after fresh/upgraded equality and restore rehearsal. Old application binaries are not presumed safe against the new schema; rollback means stop service and restore the pre-upgrade database/configuration with the matching old application, while retaining required key backups. The implementation must document disk/replay needs and recovery limits in the operator upgrade guide.
