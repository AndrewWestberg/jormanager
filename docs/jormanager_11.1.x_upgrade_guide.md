Upgrade any JorManager `11.0.x` installation to `11.1.x` with the following manual steps before relying on dashboard node monitoring.

`11.1.x` switches node monitoring to tracing-forward sockets. Database backfills in JorManager will populate tracing metadata for legacy core and relay nodes, but they do not rewrite existing remote node files for you. You must update each managed node's config, env, and startup command manually.

## Which nodes need manual changes

- All existing `core` nodes created under `11.0.x`
- All existing `relay` nodes created under `11.0.x`
- Existing parent cores that host pool credentials

Pool child nodes do not expose their own tracing listener, but the parent core service they share must be updated.

## Recommended tracing values

- `TRACING_HOST=0.0.0.0`
- `TRACING_PORT=<PROM_PORT + 1>`

If `PROM_PORT + 1` is already occupied on the host, choose the next free TCP port and keep that same value in both the env file and startup command.

## 1. Update the managed config

Edit each node's `config.json` and make sure it uses the dispatcher/forwarder tracing shape generated by `11.1.x`.

If you need a reference while manually editing `config.json`, use the published example config files at:

- `https://bluecheesestakehouse.com/jormanager/`

Required expectations:

- `UseTraceDispatcher` is `true`
- `TurnOnLogging` is `true`
- `TurnOnLogMetrics` is `true`
- `minSeverity` is `Critical`
- `TraceOptions[""]` includes `Forwarder`
- `TraceOptions[""]` includes `PrometheusSimple suffix <PROM_LISTEN> <PROM_PORT>`
- `TraceOptionForwarder` is present
- legacy top-level EKG settings such as `EKGBackend`, `hasEkg`, `hasEKG`, and `hasPrometheus` are removed

## 2. Update the env file

Edit each node's `env` file and add tracing variables.

Example:

```bash
TRACING_HOST=0.0.0.0
TRACING_PORT=12790
```

Keep the existing node-specific variables already present in the file.

For parent cores that host pool credentials, make sure the shared env file also keeps these tracing variables after any manual edits.

## 3. Update systemd or manual startup scripts

Your node startup command must include the tracing listener flag:

```bash
--tracer-socket-network-accept ${TRACING_HOST}:${TRACING_PORT}
```

For systemd-managed nodes, update the `ExecStart=` command in the node service unit.

For manually managed nodes, update `startNode.sh` or the equivalent startup command.

## 4. Reload and restart

If you use systemd:

```bash
sudo systemctl daemon-reload
sudo systemctl restart <node-name>-node.service
```

If you use manual scripts, restart the node with the updated script after saving the env file.

## 5. Verify the tracing listener

Confirm the node is listening on the configured tracing port:

```bash
ss -tulw | grep <TRACING_PORT>
```

If the node host has a firewall enabled, allow the tracing port from the machine running JorManager. For example, with `ufw` you may need a rule such as:

```bash
sudo ufw allow from <JORMANAGER_IP> to any port <TRACING_PORT> proto tcp
```

Without a matching firewall rule, JorManager will not be able to connect even if the node process is listening locally.

Confirm the service started cleanly:

```bash
sudo systemctl status <node-name>-node.service
```

Or inspect your manual startup logs if you do not use systemd.

## 6. Verify JorManager monitoring

After the node restarts:

- open the JorManager dashboard
- confirm the node shows live stats again
- confirm legacy relays and cores no longer stay stuck with null stats

If stats remain null, re-check that:

- the env file contains both `TRACING_HOST` and `TRACING_PORT`
- the startup command includes `--tracer-socket-network-accept ${TRACING_HOST}:${TRACING_PORT}`
- the selected tracing port is actually listening
- the config still includes the dispatcher/forwarder tracing shape
