Critiquer: Iteration 1
Timestamp: 2026-05-14T21:59:26Z

Reviewed the required docs, the task-204 contract artifacts and review history, and the live runtime seams in `NodeMonitor.kt`, `NodeStats.kt`, `EkgService.kt`, `BlockMonitor.kt`, `PooltoolMonitor.kt`, `Configuration.kt`, and `src/main/kotlin/com/swiftmako/jormanager/tracing/`. The plan is close, but it still leaves two runtime contracts and one lifecycle requirement too open for an implementation pass that is supposed to remove the old path cleanly.

Blocking findings:
- The plan does not pin the non-core behavior tightly enough, and that is now a product/runtime contract issue, not just an implementation detail. Live `NodeMonitor` still monitors every non-pool node (`src/main/kotlin/com/swiftmako/jormanager/monitors/NodeMonitor.kt:203-230`), not just cores, while the proposed task scope narrows direct node-state support to cores only (`.agent/plans/cardano-node-jormanager-tracing/task-plans/task-301.md:152-155`). The plan says non-core nodes should “either skip monitoring them or emit null-valued stats only if that matches the current live consumer expectation discovered during implementation,” which is too open. That must be decided before coding because the default-node fast path depends on `latestNodeStats`, and nothing in live wiring guarantees the default node is a core node.
- The plan is internally inconsistent about the `DataPoint` fetch model versus the promised 5-second `NodeMonitor` cadence. `SocketDataPointSessionClient` currently sends exactly one request on connect and then only reads replies until `Done` (`src/main/kotlin/com/swiftmako/jormanager/tracing/DataPointSessionClient.kt:32-70`). The plan simultaneously says to preserve `NodeMonitor`’s 5-second polling cadence and to add one “long-lived” sibling `DataPoint` session per core node (`task-301.md:19, 145-150`). That is not a pinned implementation shape yet. The task needs to decide up front whether task-301 will: keep a long-lived connection that is explicitly re-requested on each interval, or simplify to one short request/reply session per interval. Leaving that choice to implementation is likely to cause unnecessary design churn in `tracing/`.
- The plan notices the startup-seeding risk but does not turn it into an approval requirement for the new node-state lifecycle owner. Production `nodesChannel` is still a plain unreplayed `MutableSharedFlow()` (`src/main/kotlin/com/swiftmako/jormanager/spring/config/Configuration.kt:204-209`), `BlockMonitor` still owns cold-start seeding (`src/main/kotlin/com/swiftmako/jormanager/monitors/BlockMonitor.kt:66-75`), and `TracingConnectionManager` already protects itself by self-seeding from `nodeRepository.findAll()` on startup (`src/main/kotlin/com/swiftmako/jormanager/tracing/TracingConnectionManager.kt:73-85`). Task-301 proposes a new sibling manager but does not explicitly require the same self-seeding behavior. Without that, existing nodes can be silently unmonitored depending on lifecycle ordering.

Non-blocking observations:
- The plan is correct to keep `NodeStats` unchanged and reuse `NodeStateDataPointDecoder` rather than redefining the contract. Live `NodeStats` is still only the eight pinned fields plus identity metadata (`src/main/kotlin/com/swiftmako/jormanager/model/NodeStats.kt:3-17`).
- Deferring deletion of `EkgService.kt` itself to `task-302` is reasonable. The real requirement here is removing `NodeMonitor` production use sites (`src/main/kotlin/com/swiftmako/jormanager/services/EkgService.kt`, `src/main/kotlin/com/swiftmako/jormanager/monitors/NodeMonitor.kt:235-411`).
- The plan’s preference for a narrow sibling manager instead of a generalized mixed-protocol framework matches the current codebase well. `TracingConnectionManager` is still trace-object-only today, and widening it prematurely would add risk without clear payoff.
- The verification section should also explicitly check that websocket payload grouping still occurs on the existing `/topic/messages` `nodestats` path, because the Vue store still consumes that exact shape (`vue/src/stores/jormanager.ts:422-648`).

Approval bar:
- Revise the plan to pin the exact behavior for relay and pool nodes in task-301, including what happens when the default node is not an eligible core node and whether `latestNodeStats` can legitimately stop updating for that case.
- Revise the plan to pin the `DataPoint` query cadence model explicitly: repeated short-lived request/reply sessions, or a true long-lived session with repeated requests. Do not leave that as an implementation-time choice.
- Revise the plan so any new node-state connection manager must self-seed existing eligible nodes on startup, not just consume `nodesChannel`, to avoid the current unreplayed shared-flow timing hazard.

Decision: requires_changes
