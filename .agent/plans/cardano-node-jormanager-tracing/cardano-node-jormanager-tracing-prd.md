# Cardano Node And JorManager Tracing Migration PRD

## Overview

This PRD defines the accepted design for migrating JorManager-managed Cardano
nodes from the legacy file-based tracing configuration to the modern
`UseTraceDispatcher` tracing system available in `cardano-node 11.0.1+`, while
also replacing JorManager's SSH log scraping and HTTP EKG or Prometheus polling
with direct Hermod-compatible node protocol consumers implemented inside
JorManager itself.

The target design keeps machine-formatted logs flowing to stdout for journald on
all managed nodes, enables direct trace forwarding only on core nodes, and has
JorManager connect directly to each core node as the only external integration
consumer. Direct JorManager <-> node Hermod-compatible protocols are the only
accepted integration boundary in this plan. JorManager will use that boundary
for internal live event consumption, starting with block-event ingestion that
currently powers `BlockMonitor`, and extending to the node-state data that
currently powers `NodeMonitor`.

This document is intentionally a design and implementation-spec PRD, not a task
graph. The goal is to lock architecture, invariants, scope boundaries, and code
touch points before generating the tasks JSON.

## Problem Statement

JorManager currently relies on the old Cardano tracing and metrics surfaces in
four ways:

1. node configs generated by JorManager still assume legacy tracing and rotating
   file output
2. JorManager's `BlockMonitor` discovers block events by SSHing into each node
   host and scraping `logs/node.json` and rotated `logs/node-*.json` files
3. JorManager's `NodeMonitor` polls node-local or SSH-tunneled EKG HTTP
   endpoints for dashboard node stats
4. JorManager node creation and generated configs still carry EKG and
   Prometheus HTTP port assumptions

That approach is no longer aligned with modern `cardano-node` releases:

- new node versions support the dispatcher-based tracing system
- the dispatcher model is designed around stdout and forwarding rather than
  in-node rotating file scribes
- EKG and Prometheus HTTP exposure are no longer a stable integration boundary
  for JorManager planning
- durable historical retention is expected to be handled outside the node,
  which in this deployment means journald rather than a JorManager-owned log
  archive

The migration problem is therefore not just "update config keys." It is:

1. how to generate only new-style tracing config for all newly created nodes
2. how to preserve machine-readable journald output for human forensics on every
   node
3. how to enable direct trace forwarding only where JorManager actually consumes
   it
4. how to replace SSH file scraping with a clean long-term tracing consumer
   inside JorManager
5. how to replace EKG and Prometheus HTTP polling with direct Hermod-compatible
   node protocol consumers for node-state data
6. how to preserve current block discovery and dashboard semantics without
   introducing unnecessary backward compatibility or runtime complexity

## Goals

- Generate only new tracing configs for newly created JorManager-managed nodes.
- Remove all legacy tracing configuration from JorManager-generated node
  configs.
- Remove EKG and Prometheus HTTP configuration from JorManager-generated node
  configs.
- Keep machine-formatted stdout logging enabled for journald on all nodes.
- Enable forwarding automatically for core nodes only.
- Have each forwarded core node support the required direct Hermod-compatible
  JorManager session set.
- Have JorManager connect out directly to each core node over a dedicated
  tracing TCP port.
- Replace `BlockMonitor` SSH log scraping with a direct tracing consumer.
- Replace `NodeMonitor` EKG and Prometheus HTTP polling with direct
  Hermod-compatible node protocol consumption.
- Preserve current block discovery semantics where live trace events discover
  candidate blocks and chain data later classifies them as forged, missed, or
  orphaned.
- Preserve the current `NodeStats` contract where practical while changing its
  underlying data source.
- Establish a clean long-term tracing subsystem in JorManager that can later be
  extended to consume more event families and node-state subscriptions.

## Non-Goals

- Supporting legacy tracing and new tracing at the same time.
- Maintaining backward compatibility with `cardano-node` versions earlier than
  `11.0.1`.
- Using the `cardano-tracer` executable as part of the runtime design.
- Running `hermod-rust`, `hermod-tracing`, or any other tracing sidecar as part
  of the runtime design.
- Having JorManager read journald for recovery or historical replay.
- Reconstructing missed historical trace events after JorManager downtime.
- Adding a UI surface for tracing configuration, tracing health, or tracing
  toggles in the first version.
- Keeping EKG or Prometheus HTTP scraping as a fallback path.
- Supporting forwarding on relay or pool nodes in the first version.
- Updating existing deployed nodes in place automatically.
- Updating db-sync config templates.
- Creating the tasks JSON in this pass.

## Locked Planning Decisions

- All newly created JorManager-managed nodes use new tracing with
  `UseTraceDispatcher: true`.
- JorManager supports this tracing migration only for `cardano-node 11.0.1+`.
- All newly created nodes continue writing machine-formatted logs to stdout for
  journald.
- Direct JorManager <-> node Hermod-compatible protocols are the only accepted
  external integration boundary.
- Generated configs should start from Markus's full tracing baseline and then
  apply the minimal JorManager-owned mutations required for dispatcher
  enablement, node-local ports, and core-node forwarding, while stripping all
  EKG and Prometheus HTTP exposure.
- Legacy tracing config should be removed from generated configs except for the
  compatibility-era keys still required by `cardano-node 11.0.1` startup or
  retained by the accepted upstream config shape.
- Core nodes automatically enable forwarding and listen for a tracing client.
- Relay and pool nodes do not enable forwarding in the first version.
- JorManager is always the client and node is always the listener.
- JorManager connects directly to the node host using `host.hostname`.
- Tracing listeners bind on all interfaces and are restricted by firewall
  outside JorManager.
- Each core node gets its own dedicated tracing port.
- Tracing forwarding is not exposed as a UI option in the first version.
- JorManager is the only live tracing consumer.
- JorManager does not query journald and does not perform historical recovery.
- Missing events after the node's forwarder buffer window are acceptable.
- For `cardano-node 11.0.1`, the block-discovery event to consume remains
  `TraceAdoptedBlock`.
- JorManager should match forwarded adopted-block events by forwarded namespace
  `Forge.AdoptedBlock` and machine payload field `kind: "TraceAdoptedBlock"`.
- JorManager should treat forwarded tracing payloads as `TraceObject` wrappers
  that carry machine JSON in `toMachine`, not as the old scraped log-line shape
  with outer `at` / `env` / `data` / `host` fields.
- The per-node forwarder buffer defaults should come from the accepted research
  baseline unless `cardano-node 11.0.1` verification requires different safe
  defaults.
- JorManager should implement only the minimum tracer-client functionality
  needed for its own use cases and should not depend on `cardano-tracer` or a
  Hermod sidecar.
- JorManager must not scrape node HTTP endpoints for EKG or Prometheus.
- Generated configs must not include `EKGBackend`, `PrometheusSimple`,
  `hasEkg`, `hasEKG`, or analogous HTTP metrics bindings.
- JorManager should consume both block events and the node-state data needed by
  `NodeMonitor` through Hermod-compatible protocols, but those data families may
  land in separate implementation steps.
- Phase 1 live consumption scope is the protocol foundation plus block
  discovery. Node-state migration off EKG and Prometheus HTTP polling is the
  next workstream in the same overall migration and should reuse the same direct
  Hermod-compatible integration boundary.
- The subsystem should be designed to support future event families such as
  missed leadership checks and errors without an architectural reset.
- Existing deployed nodes are not auto-modified; this plan targets newly
  created nodes and documents manual migration expectations for older nodes.
- The deployed node template configs in `/home/westbam/bcsh/jormanager/` must
  be updated before rollout is considered complete for newly created nodes, but
  that environment-facing alignment work does not block the core automated app
  implementation.
- The `*-db-sync-config.json` files in `/home/westbam/bcsh/jormanager/` are out
  of scope for this migration.

## Requirements

### Functional Requirements

- JorManager-generated configs must set `UseTraceDispatcher: true` for all node
  types.
- All generated configs must emit machine-formatted logs to stdout.
- All generated configs must use Markus's full tracing baseline as the source
  tracing config.
- All generated configs must remove EKG and Prometheus HTTP configuration.
- The deployed node template configs used for new node creation in
  `/home/westbam/bcsh/jormanager/` must be updated for `guild`, `mainnet`,
  `preprod`, and `preview`.
- Core node configs must include forwarding.
- Relay and pool node configs must not include forwarding.
- Core nodes must be provisioned with a dedicated tracing listener port.
- JorManager node creation must store the tracing port in the database for core
  nodes.
- JorManager-generated startup wiring must configure the core node tracing
  listener so JorManager can connect to it.
- `BlockMonitor` must stop tailing `logs/node.json` and rotated log files.
- `BlockMonitor` must stop using SSH log scraping for block discovery.
- JorManager must connect directly to each core node and consume forwarded live
  trace events.
- `NodeMonitor` must stop polling node HTTP endpoints for EKG or Prometheus.
- `NodeMonitor` must stop using SSH port-forwarding as a transport for HTTP
  metrics collection.
- JorManager node creation must stop requiring EKG and Prometheus HTTP port
  inputs for new nodes.
- JorManager must continue using trace-driven discovery plus chain-data-driven
  validation for forged, missed, and orphaned block outcomes.
- JorManager must continue publishing the node dashboard stats currently carried
  by `NodeStats` through a direct Hermod-compatible protocol path for core nodes
  in the first node-state migration version.
- Relay and pool node-state migration are out of scope until their direct
  protocol transport and port model are explicitly defined.
- JorManager must maintain the required direct Hermod-compatible session or
  sessions per forwarded core node.

### Non-Functional Requirements

- Prefer a clean long-term tracing subsystem over a minimal one-off patch in
  `BlockMonitor`.
- Reuse existing JorManager socket-client patterns and repository seams where
  that reduces complexity truthfully.
- Do not add backward-compatibility code for legacy tracing.
- Do not add or preserve HTTP EKG or Prometheus fallback code.
- Do not add journald integration, trace persistence, or replay logic in the
  first implementation.
- Keep node service generation and environment file conventions as stable as
  possible while making the required tracing changes.
- Keep frontend changes minimal and internal-only where possible.
- Keep queue sizing internal and non-user-configurable in the first version.

## Existing Foundation

JorManager already provides two important foundations for this migration.

### Existing SSH/File Ingestion

`BlockMonitor` currently performs both a historical scrape and a live tail using
local shell execution or remote SSH execution:

- historical scrape of `logs/node-*.json`
- live tail of `logs/node.json`
- filtering on `TraceAdoptedBlock`

This is the behavior that must be replaced for new tracing.

### Existing Direct Node Socket Client Infrastructure

JorManager already contains a durable direct node client stack used by
`ChainMonitor` and `PooltoolMonitor`, including:

- `Mux`
- `HandshakeProtocol`
- `KeepAliveProtocol`
- `ChainSyncProtocol`
- `BlockFetchProtocol`

This means the repository already embraces long-lived outbound TCP client
connections from JorManager to a Cardano node process. The new tracing client
should align with that architecture style, while remaining separate from the
node-to-client mini-protocol stack.

## Architecture Direction

### Why Stdout Plus Forwarding

The accepted model uses both stdout and forwarding because it cleanly separates
durability from live integration:

- stdout machine logs go to journald for human-operated historical retention
- forwarding gives JorManager a low-latency live event stream

This keeps JorManager focused on online event consumption rather than historical
log retrieval.

### Why Forwarding Only On Core Nodes

The current runtime use case is block discovery from core-node logs. Pool nodes
do not need a separate forwarded stream because their log stream is already part
of the same underlying core-node process model the user described. Relays do not
need forwarding in the first version because JorManager has no active consumer
for their log stream.

### Why Direct Connect Rather Than SSH Tunneling

The accepted network model is direct outbound TCP from JorManager to each core
node listener. This avoids embedding SSH transport complexity into the new
tracing subsystem and matches the current direct-connect architecture already
used by the node client monitors.

### Why Hermod-Compatible Protocols Only

The accepted integration model is protocol compatibility rather than a runtime
dependency on a Hermod process:

- JorManager talks directly to the node over Hermod-compatible protocols
- JorManager does not depend on a `hermod-tracer`, `hermod-acceptor`, or
  `cardano-tracer` sidecar
- JorManager does not depend on node-local HTTP surfaces for EKG or Prometheus

This keeps the production architecture to JorManager <-> node only while still
aligning with the upstream tracing direction.

## Node Config Generation Design

### Global Tracing Shape

All generated configs should move to the dispatcher shape:

- `UseTraceDispatcher: true`
- `TraceOptionForwarder` on core nodes
- `TraceOptions`
- compatibility-era keys still required by the accepted `11.0.1` config shape

This migration includes both:

- JorManager's app-side config generation logic
- the deployed node template configs in `/home/westbam/bcsh/jormanager/` that
  JorManager pulls down for new node creation

The generated tracing baseline should come from `config-markus.json`, then be
normalized into the accepted `cardano-node 11.0.1` dispatcher-era shape.

The root `TraceOptions[""]` policy should therefore preserve Markus's baseline
behavior:

- `Stdout MachineFormat`

Core nodes then add:

- `Forwarder`

And the generated config should additionally include the accepted dispatcher-era
top-level tracing keys from the `11.0.1` config shape, including only the
compatibility-era non-HTTP keys required by the node's config shape.

### Legacy Tracing Removal

Generated configs should no longer include or mutate legacy tracing structures
such as:

- `TraceBlockFetch...` boolean families
- `TracingVerbosity`
- `defaultBackends`
- legacy `defaultScribes` values tied to file outputs
- `setupBackends`
- legacy `setupScribes`
- `rotation`
- `KatipBK`
- `FileSK`
- `EKGBackend`
- `PrometheusSimple`
- `hasEkg`
- `hasEKG`
- `TraceOptionMetricsPrefix`
- `TraceOptionResourceFrequency` when retained only to support HTTP metrics

The only legacy-shaped keys that remain should be the compatibility-era keys
still present in the accepted `11.0.1` config shape. This is not a license to
carry forward file-scribe behavior or HTTP metrics exposure.

The same legacy-removal rules apply to the deployed node template configs in
`/home/westbam/bcsh/jormanager/` for `guild`, `mainnet`, `preprod`, and
`preview`.

### Markus Baseline Policy

`config-markus.json` is the source-of-truth baseline for the generated tracing
configuration. JorManager should preserve that baseline logging profile and only
apply the minimal required mutations for dispatcher-era config shape, node-local
port assignment, and core-node forwarding. The preserved baseline does not
extend to Markus's EKG or Prometheus HTTP assumptions when generating new node
configs for this plan.

### Forwarder Queue Defaults

Core nodes should receive internal default forwarder queue settings from the
accepted research baseline unless implementation verification against
`cardano-node 11.0.1` requires a different safe default. The design should
recognize that the actual buffer window is event-rate-based, not time-based.
Queue sizing stays internal for this version.

## Node Creation And Startup Design

### Data Model

Add a tracing port column to the `nodes` table and corresponding backend entity
model.

- core nodes receive an allocated tracing port
- relay and pool nodes do not need one in the first version

### Port Allocation

Accepted default strategy:

- for core nodes, start from `12790`
- if occupied, scan upward until a free port is found

This keeps node-local operational ports grouped together while avoiding a
dependency on EKG or Prometheus port adjacency.

### Startup Wiring

The generated node runtime must configure a tracing listener for core nodes.
Depending on exact `cardano-node 11+` support, this may live in either:

- generated config
- generated systemd unit / manual start scripts
- or both

The implementation must verify the exact listener configuration mechanism for
the node version target before final coding.

## JorManager Tracing Subsystem Design

### High-Level Shape

JorManager should gain a dedicated tracing subsystem rather than embedding the
new protocol directly inside `BlockMonitor`.

Suggested responsibilities:

- connection management per core node
- protocol/session lifecycle
- event decoding and normalization
- block-event handoff into the existing block repository and validation flow
- node-state handoff into the existing dashboard `NodeStats` flow

### Initial Subsystem Components

The exact class names can change, but the design should converge on a shape
close to:

- `TracingConnectionManager`
- `TracingClient`
- `TracingEventDecoder`
- `TracingBlockEventService`
- `TracingNodeStateService`
- `CoreNodeTraceMonitor`

### Reuse Boundaries

The tracing subsystem should reuse patterns from `ChainMonitor` and related
socket-based monitors where they provide stable lifecycle behavior, but it
should not pretend that the forwarding protocol is the same thing as the
existing node-to-client mini-protocol family.

## BlockMonitor Migration Design

### Current Behavior To Preserve

The accepted runtime semantics are:

- trace events discover candidate completed/adopted blocks
- chain state later verifies and classifies them as forged, missed, or orphaned

That behavior should stay intact after migration.

### Behavior To Remove

The following assumptions should be removed completely from the new path:

- `logs/node.json`
- `logs/node-*.json`
- `tail -Fn0`
- `grep --line-buffered 'TraceAdoptedBlock'`
- SSH or local shell log scraping for block discovery

### New Behavior

`BlockMonitor` should be refactored so that block discovery comes from live
tracing events instead of file lines. The downstream repository writes and later
validation flow should be preserved where possible rather than rewritten.

The current `TraceAdoptedBlock` line-parser model should not be assumed to match
the forwarded tracing payloads. The new tracing subsystem may need a different
decode path and should normalize forwarded events into an internal block-event
model before handing them to the existing persistence and validation flow.

For `cardano-node 11.0.1`, upstream source confirms that the adopted-block
event is still rendered with machine field `kind: "TraceAdoptedBlock"` and
includes at least:

- `kind`
- `slot`
- `blockHash`
- `blockSize`

At higher detail levels the renderer can additionally include:

- `txIds`

JorManager Phase 1 should depend only on `slot` and `blockHash`, and may ignore
`blockSize` and any optional `txIds`.

## Event Scope Design

### Phase 1

Phase 1 only needs to support the direct-protocol foundation and live event flow
required to replace `BlockMonitor` block discovery.

For `cardano-node 11.0.1`, that means consuming forwarded `TraceObject`s whose
normalized namespace is `Forge.AdoptedBlock` and whose `toMachine` JSON payload
contains `kind: "TraceAdoptedBlock"`.

Phase 1 should also pin down the exact automated listener/startup mechanism and
the protocol fixtures needed for agent-driven implementation and testing.

### Phase 2

Phase 2 replaces `NodeMonitor` EKG and Prometheus HTTP polling with direct
Hermod-compatible node-state consumption while preserving the current
`NodeStats` contract where practical.

Before the `NodeMonitor` refactor begins, the implementation must pin the exact
node-state protocol family used in this version, rather than leaving it open
between forwarded trace objects, data-point exchanges, or a future subscription
model.

That pinning is now satisfied by the direct `DataPoint` mini-protocol with the
exact eight-key `cardano.node.metrics.*` request set used by the current
`NodeStats` contract, a sibling-per-core-session topology, and literal request
or reply fixture anchors that cover both normal and chunked-byte-string
`DataPointValue` payloads.

### Future-Ready Scope

The subsystem should be designed so future event types can be added without
another architectural reset. The most likely next event families are:

- node was leader but did not forge or adopt its own block
- error events

Those event families are out of scope for the first implementation but should
not be made harder by the initial design.

## NodeMonitor Migration Design

### Current Behavior To Preserve

The accepted runtime semantics for node dashboard updates are:

- `NodeMonitor` publishes the fields currently exposed by `NodeStats`
- websocket delivery shape remains stable where practical
- the default-node fast path remains intact where practical

The current node-state fields to preserve are:

- peers
- incomingPeers
- blockHeight
- remainingKESPeriods
- epoch
- slot
- slotInEpoch
- txsProcessed

### Behavior To Remove

The following assumptions should be removed completely from the new path:

- EKG HTTP polling
- Prometheus HTTP scraping
- SSH port-forwarding used only to reach node HTTP endpoints
- node creation flows that require EKG or Prometheus HTTP port inputs

### New Behavior

`NodeMonitor` should be refactored so that node-state data comes from direct
Hermod-compatible protocol consumption rather than HTTP endpoints. The exact
message family may be forwarded trace objects, data-point style exchanges, or a
future upstream subscription model, but the integration boundary stays the same:
JorManager connects directly to the node and does not require an intermediate
Hermod or tracer process.

For the first node-state migration version, this direct node-state path applies
to core nodes only. Relay and pool parity are explicitly deferred until their
direct protocol transport shape is pinned down.

## Persistence And Recovery Design

JorManager is intentionally not a durable historical trace store in this design.

- stdout and journald are the durable human forensics surface
- forwarding is the live ephemeral integration surface
- node-side buffering covers short JorManager downtime only
- JorManager does nothing special after long downtime and simply resumes live

No journald access, no event replay, and no trace-event persistence are part of
the first version.

## Rollout Plan

### Newly Created Nodes

Newly created nodes become the primary supported rollout target for this design.
That rollout depends on both JorManager code changes and updated deployed node
template configs in `/home/westbam/bcsh/jormanager/`.

### Existing Nodes

Existing nodes are not modified automatically. The rollout documentation should
state that older deployments need manual recreation or manual node-side changes
to adopt the new tracing-forwarder model.

Updating the deployed template configs does not auto-migrate existing nodes; it
only changes the tracing shape inherited by newly created nodes.

## Risks

- Exact `cardano-node 11.0.1+` tracing listener configuration must be verified before
  coding startup generation.
- Forwarder queue sizing is approximate because node retention is event-rate
  based, not time based.
- Future Hermod-compatible protocol changes upstream may require JorManager-side
  client maintenance.
- Removing file-log assumptions means the migration must complete cleanly; there
  is no dual-mode support in this plan.
- Replacing HTTP EKG and Prometheus polling requires preserving dashboard
  semantics from a different protocol family.

## Open Questions

- The core-node listener mechanism is now pinned by implementation and test
